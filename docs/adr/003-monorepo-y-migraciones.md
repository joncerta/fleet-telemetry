# ADR-003 — Monorepo base, runner de migraciones y roles de base de datos

- **Estado:** aceptado
- **Fecha:** 2026-10-04
- **Nota de numeración:** el ADR-002 está reservado para la persistencia (fase 1d).

## Decisiones

1. **`typecheck`, `lint` y `test` dependen de `^build`.** Los paquetes internos se consumen desde `dist/`, y el hook corre sobre un checkout sin `dist/`. Turbo construye lo necesario y lo cachea. Se descartó resolver desde el código fuente con condiciones de `exports` personalizadas: añade configuración en tsc, vitest y tsx para ahorrar un `tsc` cacheado.
2. **`tsx` en desarrollo y `node dist/` en producción.** tsx reescribe los imports `.js` a `.ts` y permite `--watch`; el type stripping nativo de Node no los reescribe. `db:migrate` corre con tsx para no exigir un build previo.
3. **Tres niveles de test por nombre:** `*.test.ts` (unitario, sin red ni DB), `*.int.test.ts` (integración) y `tests/e2e/**/*.e2e.test.ts`. `tests/e2e` es un paquete privado del workspace para que Turbo le pase las variables de entorno. Integración y e2e no usan caché y se ejecutan con `--concurrency=1`: las bases temporales comparten los roles del cluster.
4. **Pureza de `domain/` por ESLint** (`@fleet/eslint-config`), con **lista blanca**: `domain/` solo importa rutas relativas **que resuelven dentro de `domain/`**, `zod`, `@fleet/contracts`, `vitest` y `node:assert`/`node:util`. Una lista negra de paquetes deja pasar el siguiente que se instale (`pino`, `axios`, `ioredis`...). Las rutas relativas las comprueba una regla propia, `fleet/domain-relative-imports` (en el mismo paquete, **sin dependencias nuevas**): resuelve el especificador contra el archivo con `path.resolve` y rechaza todo lo que salga de la carpeta `domain/` más cercana (`../config/env.js`, `../../packages/...`, `application/`, `infrastructure/`, `interfaces/`), también en `export ... from` e `import type`. Se descartó `import-x/no-restricted-paths` y `eslint-plugin-boundaries`: piden declarar zonas por servicio y un resolver, y añaden una dependencia para algo que son diez líneas. `no-restricted-globals` prohíbe los globales con I/O, reloj o entropía (`fetch`, `process`, `console`, `crypto`, timers, `WebSocket`, `EventSource`, `XMLHttpRequest`, `Buffer`, `performance`, `global`) y `globalThis`, que da acceso a todos. `no-restricted-syntax` prohíbe `new Date()` sin argumentos, `Date()`, `Date.now` y `Math.random`, y sus alias: guardar `Date` o `Math` en una variable (`const D = Date`, `const { now } = Date`, `const { random } = Math`, `x = Date`) y `Reflect.construct(Date, ...)`: el tiempo y la aleatoriedad entran por puertos (por ejemplo un `Clock` en `application/`); `Date` como tipo y `new Date(valor)` siguen permitidos. `import()`, `require()`, `import x = require()` y tipos `import("...")` siguen prohibidos. **Lo que sigue sin cubrirse** (es una barrera contra descuidos, no contra quien quiera saltarla): un identificador local con el nombre de un global (`const process = ...`); el reloj o la entropía por vías que no nombran `Date` ni `Math` como identificador de una declaración, asignación o `Reflect.construct`, como `Reflect.apply(Date, ...)`, `Date.call(...)`, `Date.bind(...)` o `[Date][0]`; un alias que se construye con otra expresión (`const D = cond ? Date : Date`, `const D = (0, Date)`, un parámetro por defecto `(D = Date) => ...`, una propiedad de objeto `{ clock: Date }`); y un `Date` o `Math` que llegue desde fuera del dominio (un argumento o un puerto que `application/` implemente con el reloj real). La regla también marca usos deterministas guardados en una variable (`const { parse } = Date`): se escribe `Date.parse(...)` en el sitio de llamada. La defensa de fondo es la revisión y que el dominio reciba el tiempo como argumento o por un puerto. Está probada con la API de ESLint. La caché de Turborepo incluye `eslint.config.js` y `packages/eslint-config/src/**` en las entradas de `lint` (`inputs` con `$TURBO_ROOT$`), y cada paquete con script `lint` declara `eslint` y `@fleet/eslint-config`.
5. **Migraciones reversibles.**
   - **Ejecución:** `pg_advisory_lock` en sesión dedicada (el mismo para `migrate` y `rollback`) y una transacción por migración. **Migraciones sin transacción (fase 1b, S1):** lo que Postgres o Timescale prohíben dentro de una transacción (`CREATE INDEX CONCURRENTLY`, un continuous aggregate `WITH DATA`, `refresh_continuous_aggregate`) se escribe en una migración cuya **primera línea** es `-- migrate:no-transaction`, y el **down** del par debe llevar el mismo marcador (el cargador falla, sin tocar la base, si solo uno lo lleva: un up sin transacción con un down transaccional dejaría una reversión que no se puede ejecutar como se escribió). El runner la ejecuta **sentencia por sentencia** (un script con varias sentencias es UNA transacción implícita en el protocolo simple de Postgres, y ahí `CONCURRENTLY` falla; por eso `splitSqlStatements` divide respetando comentarios, comillas, identificadores y cadenas entre dólares, y el script no puede usar metacomandos de `psql`) y registra la fila de `schema_migrations` **después** del éxito de todas; el down borra la fila al final. Sigue bajo el mismo advisory lock. **Contrato: la migración tiene que ser idempotente sentencia por sentencia** (`IF NOT EXISTS`, `IF EXISTS`, `CREATE OR REPLACE`...), porque sin transacción no hay reversión: si una sentencia falla, las anteriores quedan hechas y la migración NO queda registrada, así que el siguiente `db:migrate` la ejecuta entera desde la primera sentencia (y mientras no esté registrada se puede corregir el script; una vez registrada, el checksum impide editarlo); si muere el proceso entre el último efecto y el registro, igual. El marcador forma parte del checksum. Un down que falla a mitad deja la migración registrada como aplicada y se repite con `db:rollback` cuando desaparece la causa (el down aplicado no se edita). Probado en `no-transaction.int.test.ts` con un par de prueba en un directorio temporal: `CREATE INDEX CONCURRENTLY` pasa (el control con el mismo SQL en una migración transaccional falla), repetirla o completarla tras un fallo es idempotente, respeta el advisory lock (otra sesión con el lock la impide; dos `migrate()` concurrentes la aplican una vez) y el down corre igual sin transacción.
   - **Convención:** cada migración es un par `NNN_<nombre>.sql` (up) y `NNN_<nombre>.down.sql` (down), obligatorio. El cargador falla, sin tocar la base, si un up no tiene down, si un down no tiene up, si los nombres de la misma versión no coinciden o si un número se repite. La reversibilidad se hace cumplir de forma mecánica, igual que el checksum hace cumplir "nunca se edita una existente".
   - **`schema_migrations`:** guarda el sha256 del up (`checksum`) y del down (`down_checksum`). El checksum normaliza CRLF a LF (git `autocrlf` en Windows). `migrate` falla si una migración aplicada cambia (up o down), desaparece o se renombra, y si una pendiente tiene un número menor que la última aplicada. La tabla evoluciona de forma idempotente (`ADD COLUMN IF NOT EXISTS`): en las filas anteriores a la columna, `migrate` o `rollback` registran el checksum del down la primera vez, solo si el up sigue intacto, sin reaplicar nada ni recrear la base.
   - **`pnpm db:rollback`:** por defecto revierte solo la última migración aplicada; `--steps N` revierte las últimas N y `--to NNN` revierte todas las posteriores a NNN (la NNN queda aplicada; `--to 0` las revierte todas, y una versión no aplicada es un error). Valida el checksum del up y del down de **todas** las seleccionadas antes de ejecutar ninguna; cada down corre en su propia transacción junto con el borrado de su fila de `schema_migrations`. Registra qué va a revertir y qué revirtió. Sin nada aplicado no hace nada (ni crea la tabla de control) y sale con 0.
   - **`pnpm db:status`:** de solo lectura (sesión con `default_transaction_read_only`, sin lock, sin crear ni alterar la tabla de control). Lista aplicadas y pendientes y sale con 1 si hay una discrepancia (checksum del up o del down, migración borrada o renombrada, número fuera de orden). Las pendientes no hacen fallar el comando: quien necesite exigirlas vacías (`/e2e-check`) lee la sección `Pendientes`. Es un script aparte y no `db:migrate --status` para que el verbo que cambia la base no tenga un modo que no la cambia, y porque solo necesita `DATABASE_ADMIN_URL` (no las contraseñas de los roles).
   - **Guarda de roles (001 down):** `fleet_app` y `fleet_ro` son del cluster, no de la base. El down revierte en orden inverso (privilegios por defecto, privilegios del esquema y de la base, extensiones). Antes de `DROP ROLE` consulta `pg_shdepend` con el `dbid` de `current_database()`: si queda alguna dependencia de esos roles en **esta** base (un grant olvidado, un privilegio por defecto de otro rol), falla con `RAISE EXCEPTION` y la transacción se revierte. Solo después intenta `DROP ROLE` y tolera `dependent_objects_still_exist` (`2BP01`), que a esas alturas solo puede venir de otras bases: conserva el rol con un `NOTICE`. Las extensiones se borran sin `CASCADE`: un objeto dependiente que otra migración no haya quitado en su down es un error, no un borrado silencioso. Nota: si la plantilla ya trae la extensión (como `template1` en la imagen de Timescale), el up de la 001 no la crea y el down igualmente la borra.
   - **Prueba de ida y vuelta:** un test de integración, en bases temporales **creadas desde `template0`** (sin las extensiones que la imagen instala en `template1`), toma un **baseline antes del primer up**, aplica las migraciones reales **una a una** con un snapshot tras cada up, las revierte de una en una y exige que cada estado sea idéntico al snapshot previo al up de esa migración (los snapshots se indexan por posición en la lista de archivos, no por número de versión, así que las versiones no tienen que ser consecutivas; un down que deja una columna, un índice o un grant no queda tapado por el `DROP TABLE` de una migración anterior). Exige además que el down completo deje el baseline y que el segundo up reproduzca el primero (estado y filas de control). **Qué cubre el snapshot:** extensiones; roles (por nombre: son del cluster y sobreviven mientras otra base los use, y su `LOGIN` lo da `migrate`); relaciones (tablas, vistas, secuencias, índices) fuera de `pg_catalog`, `information_schema`, `pg_toast`, los esquemas internos de Timescale y los objetos de extensiones (`pg_depend` con `deptype = 'e'`); columnas de `public` (tipo, nulabilidad, default); constraints (`pg_get_constraintdef`); índices (`pg_get_indexdef`); grants de base, esquema y tabla de `fleet_app` y `fleet_ro`; privilegios por defecto; tipos enum y dominio de `public`; **y, desde la fase 1b (H2), definiciones y no solo nombres:** funciones y procedimientos de cualquier esquema de usuario con el `md5(pg_get_functiondef)` (un `CREATE OR REPLACE` que el down no restaura cambia el md5 aunque nombre y argumentos sigan iguales; de un agregado solo cuenta la firma, porque `pg_get_functiondef` no lo admite), vistas, vistas materializadas y continuous aggregates con `pg_get_viewdef`, esquemas de usuario distintos de `public` (sin los de extensiones) y triggers con `pg_get_triggerdef` (sin los internos de las FK). Solo con `timescaledb` instalada: hypertables, `dimensions` (intervalo de chunk y particiones), `compression_settings` (segmentby y orderby por columna), continuous aggregates y la config de los jobs de usuario **normalizada**: sin `hypertable_id` ni `mat_hypertable_id` y con la hypertable materializada de un continuous aggregate **traducida a su vista** (el nombre `_materialized_hypertable_N`, `_partial_view_N`, `_direct_view_N` y `cagg_watermark(N)` llevan ids que cambian al recrear; se normalizan para comparar la definición y no el id). **Qué no cubre:** la tabla de control `schema_migrations` (sus filas se comparan aparte), datos, políticas RLS, comentarios, objetos fuera de los esquemas de usuario (los de extensiones) salvo lo listado, los parámetros de `ALTER DATABASE` y `ALTER ROLE`, el cuerpo de una vista que el usuario escriba con el id numérico de un continuous aggregate (la normalización solo reconoce los patrones de Timescale 2.30), y los permisos de columna. El test demuestra que detecta un down incompleto con pares de prueba en un directorio temporal (tabla, columna, índice, grant, función, tipo y default privilege sin revertir, y un down incompleto tras un salto de versión, 001 y 003) y, de la H2, que un down que no restaura una función o una vista reemplazadas, un atributo de función (volatilidad), una vista materializada, un trigger, un esquema, una función de otro esquema, el intervalo de chunk, los ajustes de compresión, una política (job) o un cambio de continuous aggregate (`materialized_only`) hace fallar el test; cada caso tiene su control positivo (el down que sí restaura pasa), y un continuous aggregate con datos y política de refresco (creado con una migración sin transacción) hace la ida y vuelta completa pese a que sus ids cambian. Acepta un par completo, así que cada migración futura queda probada como reversible sin escribir un test nuevo. La guarda de roles se prueba aparte: un grant olvidado en la base actual hace fallar el down, y las dependencias de otras bases lo toleran. Las bases temporales salen de `template0` porque en el contenedor local `CREATE DATABASE ... TEMPLATE template1` se bloquea 5 s y falla con "source database is being accessed by other users" (en el log aparece un worker `TimescaleDB Background Worker Scheduler for database 1` intentando conectarse a la plantilla); con `template0` no ocurre.
   - **Alcance del rollback:** solo en local, alineado con `CLAUDE.md`, con dos guardas que deben cumplirse a la vez. (1) `rollback()` rechaza, antes de conectar, un `DATABASE_ADMIN_URL` cuyo host no esté en la allowlist fija `127.0.0.1`, `localhost`, `::1` y `timescaledb` (también rechaza `?host=`, `?hostaddr=` y `?service=`, que cambiarían el host real, y `?options=`, ver más abajo). (2) Tras conectar, y antes del lock, también en `--dry-run`, exige que el servidor esté marcado como local: `current_setting('fleet.environment', true)` debe valer exactamente `local`; sin marca o con otro valor lanza `MigrationError` explicando que la base no está marcada como local. La marca la fija `docker-compose.yml` en el servidor (`-c fleet.environment=local`, también en CI); las bases temporales de los tests la heredan. La allowlist sola no basta: un túnel SSH o un `/etc/hosts` hacen que `localhost` apunte a una base remota, y esa base no tendrá la marca. Ninguna de las dos se salta con un flag del CLI ni con una variable de entorno del runner. **Excepción corregida:** `DATABASE_ADMIN_URL` con `?options=` sí las anulaba. En `pg@8.23.1`, `pg-connection-string` copia todos los parámetros de la query a la configuración y estos pisan lo que el código pasó de forma explícita; así, `?options=-c%20fleet.environment%3Dlocal` más un túnel a una base remota daba la marca a esa base y pasaba las dos guardas, y cualquier otro `?options=` reemplazaba en silencio `lock_timeout`, `idle_in_transaction_session_timeout`, `timezone` y `default_transaction_read_only` (un `status` o `--dry-run` dejaba de ser de solo lectura). Ahora `withMigrationClient` (migrate, rollback, status y dry-run) y `assertLocalDatabaseHost` rechazan cualquier `DATABASE_ADMIN_URL` con `options`, antes de conectar, leyendo la URL como la lee `pg`; el mensaje explica que la sesión de migración fija sus propios parámetros y no cita el valor ni las credenciales. `PGOPTIONS` no entra por esa vía: `pg` solo lo usa si la configuración no trae `options`, y el cliente de migración siempre lo fija. La marca sí es configuración del servidor (cualquier superusuario puede ponérsela con `ALTER DATABASE ... SET` o `ALTER SYSTEM`), así que es una barrera contra errores, no contra un administrador que quiera saltarla a propósito. En cualquier otro entorno se escribe una migración nueva que corrija el esquema. `pnpm db:rollback --dry-run` calcula y registra el plan sobre una sesión de solo lectura, sin lock, sin registrar checksums y sin crear la tabla de control. No se ejecuta sobre la base `fleet` local desde los agentes sin autorización explícita ni se automatiza en despliegues; un down que destruye datos (tablas) es responsabilidad de quien lo pide.
   - **Tiempos de la sesión:** `migrate`, `rollback` y `status` fijan `lock_timeout` (8 s por defecto, configurable con `DB_MIGRATE_LOCK_TIMEOUT_MS`, entre 1 y 60 s) e `idle_in_transaction_session_timeout` (60 s). Si una migración espera un lock más que eso, falla, se revierte y el error pide reintentar en una ventana de menos carga. Es distinto del timeout del `pg_advisory_lock` del runner (60 s), que solo serializa corridas.
6. **Contraseñas de roles (regla 12).** `ALTER ROLE` no admite parámetros. El runner calcula en el cliente el **verificador SCRAM-SHA-256** (`SCRAM-SHA-256$<iter>:<salt>$<StoredKey>:<ServerKey>`, como el `\password` de psql; validado con el intercambio de la RFC 7677) y pide al servidor la sentencia con `SELECT format('ALTER ROLE %I WITH LOGIN PASSWORD %L', $1, $2)`, con el rol y el verificador como parámetros; ejecuta el resultado, así que el cliente nunca concatena SQL y la contraseña en claro no viaja al servidor. El rol sale de una allowlist fija (`fleet_app`, `fleet_ro`). Los errores no llevan la contraseña ni la causa original, porque `pg` puede citar la sentencia. Solo se admiten contraseñas ASCII imprimibles (SASLprep es la identidad en ese rango; fuera de él el servidor normalizaría distinto). **Riesgo residual:** el servidor tiene `log_min_error_statement = error`, así que una sentencia fallida (y hay reintentos) queda en el log de Postgres, y con `log_statement = ddl` quedaría siempre; ahora el log contiene el verificador, no la contraseña. El verificador no sirve para autenticar, pero permite un ataque de fuerza bruta fuera de línea: el log del servidor se trata como material sensible y las contraseñas deben ser largas y aleatorias. `pg_stat_statements`: en la imagen `timescale/timescaledb-ha:pg17.11-ts2.30.2` no está en `shared_preload_libraries` (`timescaledb,pg_textsearch`) ni instalada, y `pg_stat_statements.track_utility` no existe; la sospecha no aplica a la configuración actual. Si alguien la precarga, las sentencias de utilidad no se normalizan, pero lo que registraría es el verificador.
7. **Los roles son del cluster:** `CREATE ROLE` captura `duplicate_object` y `unique_violation`, y `ALTER ROLE` se reintenta ante `tuple concurrently updated`, para que bases distintas del mismo cluster migren a la vez.
